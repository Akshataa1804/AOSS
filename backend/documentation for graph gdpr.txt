# GDPR Controls That MUST Exist for SRE Automation (AOSS)

## 1. Data Retention Control (Article 5(1)(e))

**Why SREs care:** logs, backups, DB tables, metrics stores

### Rule

Personal data **cannot be deleted earlier** than allowed retention
and **cannot be kept longer** than allowed retention.

### Must be in AOSS

* RetentionPolicy node
* max_retention_days field
* Enforcement on:

  * log cleanup
  * DB purge
  * backup rotation

### Block these SRE actions:

* “Delete logs older than 30 days” when retention is 90 days
* “Keep backups forever”
* “Disable log rotation”

---

## 2. Purpose Limitation (Article 5(1)(b))

**Why SREs care:** reusing data for debugging, analytics, monitoring

### Rule

Data collected for one purpose **cannot be reused** for another.

### Must be in AOSS

* ProcessingActivity node with `purpose`
* Relationship: `USES_DATA`

### Block these SRE actions:

* Using auth logs for marketing analysis
* Exporting prod data to staging for debugging
* Using customer data to test load tools

---

## 3. Lawful Basis Enforcement (Article 6)

**Why SREs care:** any automated processing

### Rule

Every processing activity **must have a legal basis**:

* Consent
* Contract
* Legal obligation
* Legitimate interest

### Must be in AOSS

* LegalBasis node
* Mandatory relationship:

  ```
  (ProcessingActivity)-[:HAS_LEGAL_BASIS]->(LegalBasis)
  ```

### Hard fail if missing

* Any job
* Any cron
* Any agent-planned task

This is **non-negotiable**.

---

## 4. Data Minimization (Article 5(1)(c))

**Why SREs care:** logs, traces, metrics

### Rule

Only **necessary personal data** can be processed.

### Must be in AOSS

* PersonalData node with type
* Allowed data categories per service

### Block these SRE actions:

* Logging full email / phone numbers
* Dumping full request payloads
* Exporting entire user tables for debugging

---

## 5. Access Control & Least Privilege (Article 32)

**Why SREs care:** infra permissions, automation roles

### Rule

Only authorized roles can perform sensitive actions.

### Must be in AOSS

* Role / Agent type
* Risk level per action
* Approval requirement

### Block these SRE actions:

* Agent deleting prod DB without approval
* Intern-level automation restarting auth services
* Auto-scaling scripts touching user data

---

## 6. Right to Erasure (Article 17)

**Why SREs care:** deletion pipelines, data sync

### Rule

Erasure requests **must be fulfilled within SLA**.

### Must be in AOSS

* ErasureRequest node
* erasure_sla_days
* Enforcement timer

### Block these SRE actions:

* Ignoring delete requests
* Deleting only primary DB but not replicas
* Deleting in one service but not others

---

## 7. Replication & Backup Coverage (Article 17 + 32)

**Why SREs care:** replicas, DR systems

### Rule

Erasure must propagate to:

* replicas
* backups (where technically feasible)
* caches

### Must be in AOSS

* Dependency relationships
* Service → Replica → Backup graph

### Block these SRE actions:

* Partial deletion
* “We deleted main DB, backups later”
* Skipping caches

---

## 8. Data Localization (Article 44–49)

**Why SREs care:** cloud regions, DR sites

### Rule

Personal data must not leave allowed regions.

### Must be in AOSS

* Region node
* Data → Region relationship

### Block these SRE actions:

* Replicating EU data to US region
* DR failover to non-EU cluster
* Cross-region backup restores

---

## 9. Logging & Auditability (Article 30, 33)

**Why SREs care:** traceability

### Rule

Processing must be auditable.

### Must be in AOSS

* Audit log for:

  * intent
  * decision
  * execution result

### Block these SRE actions:

* Disabling audit logs
* Deleting audit trails
* Running “silent” jobs

---

## 10. Breach Detection & Response (Articles 33–34)

**Why SREs care:** incidents

### Rule

Breaches must be detectable and reportable.

### Must be in AOSS

* Incident node
* Time threshold
* Escalation path

### Block these SRE actions:

* Disabling alerts on data access
* Muting security logs
* Suppressing anomaly detection

---

## 11. Human-in-the-Loop for High-Risk Actions

**Why SREs care:** destructive ops

### Rule

Some actions **must require approval**, no matter what.

### Must be in AOSS

* needs_approval flag
* risk_level = HIGH

### Always require approval:

* Bulk deletes
* Schema drops
* Firewall changes on prod
* Identity store changes

# The Full Enforcement Stack for AOSS (Clean Model)

Think of enforcement as **stacked gates**.
An action must pass **all gates** to execute.

```
Agent Intent
   ↓
1. Platform / SRE Safety Graph
   ↓
2. Organizational Policy Graph
   ↓
3. Regulatory Compliance Graph (GDPR, etc.)
   ↓
4. Environment & Change-Control Graph
   ↓
5. Execution Guardrails
```

Now let’s break these down.

---

## 1️⃣ Platform / SRE Safety Graph ✅ (MANDATORY)

**Purpose:**
Protect the system from catastrophic automation.

**Blocks things like:**

* remove OS
* format disk
* delete root FS
* disable monitoring
* wipe cluster

**Why it exists:**

* These actions are **never acceptable**
* Not legal issues — operational survival issues

**Verdict:**
✅ **Must exist**
You already reasoned about this correctly.

---

## 2️⃣ Organizational Policy Graph ✅ (MANDATORY)

This is **not GDPR**.
This is **company-specific operational policy**.

### Examples:

* “Automation cannot touch prod databases”
* “Bulk deletes require VP approval”
* “Intern-level agents cannot restart auth-service”
* “No changes during freeze window”

**Why it exists:**

* Every org has internal rules
* These rules change more often than laws
* SRE teams expect this control

**Graph models:**

* Roles
* Approval requirements
* Risk levels
* Freeze periods

**Verdict:**
✅ **Must exist**

---

## 3️⃣ Regulatory Compliance Graph (GDPR, HIPAA, RBI) ✅ (MANDATORY)

You already designed this well.

**Purpose:**

* Prevent legal violations
* Enforce retention, locality, erasure, etc.

**Key point:**

* Laws are **external constraints**
* Non-negotiable

**Verdict:**
✅ **Must exist**

---

## 4️⃣ Environment & Change-Control Graph ⚠️ (STRONGLY RECOMMENDED)

This layer protects **production stability**, not legality.

### Examples:

* Prod vs staging rules
* Change freeze windows
* Deployment timing
* Blast radius limits

**Blocks things like:**

* Restarting prod during peak hours
* Deploying without canary
* Large-scale changes during incident

**Why it matters:**

* Many outages are “technically allowed” but operationally stupid

**Graph models:**

* Environment
* Time windows
* Impact scope

**Verdict:**
⚠️ **Very good to add** (even minimal version)

---

## 5️⃣ Execution Guardrails ⚠️ (OPTIONAL BUT SMART)

This is the **last safety net**.

**Purpose:**

* Limit damage even after approval

### Examples:

* Max rows deleted per execution
* Rate limits on destructive commands
* Dry-run enforcement

**Important:**
This is **not policy**, this is **execution safety**.

**Verdict:**
⚠️ Optional, but makes the system robust

---

## ① Platform / SRE Safety Layer (Absolute Guardrails)

These are **non-negotiable, universal blocks**.

### Destructive System Actions (Always Block)

* Remove OS
* Format disk
* Delete root filesystem
* Wipe cluster
* Delete `/etc`, `/boot`, `/usr`
* Disable kernel protections

### Security-Critical Actions

* Disable firewall
* Disable SELinux/AppArmor
* Disable audit logging
* Disable IAM / auth service
* Remove encryption at rest

### Stability Killers

* Kill all processes
* Stop kube-apiserver
* Stop etcd
* Disable scheduler
* Force reboot all nodes

📌 **Result:**
No approval path. Always `DENY`.

---

## ② Organizational Policy Layer (Company Rules)

These vary per org but are mandatory controls.

### Role & Identity Controls

* Agent role (automation, intern, SRE, admin)
* Allowed actions per role
* Forbidden targets (prod vs non-prod)

### Approval Rules

* Bulk delete
* Schema changes
* Firewall updates
* Network reconfiguration
* Secret rotation

### Scope & Blast Radius

* Max nodes affected
* Max rows deleted
* Max services restarted
* Single-service vs multi-service ops

### Change Management

* Change freeze windows
* Maintenance windows
* On-call approval required
* CAB approval required

📌 **Result:**
`ALLOW`, `DENY`, or `REQUIRE_APPROVAL`.

---

## ③ Regulatory Compliance Layer (GDPR-Focused)

These are **law-driven constraints**.

### Data Retention

* Minimum retention
* Maximum retention
* Log retention
* Backup retention

### Lawful Processing

* Legal basis per processing activity
* Purpose limitation
* Data minimization

### Data Subject Rights

* Erasure SLA
* Rectification
* Access request handling

### Data Locality

* Allowed regions
* Cross-region replication
* DR region restrictions

### Backup & Replica Coverage

* Erasure propagation
* Cache invalidation
* Snapshot handling

### Audit & Traceability

* Processing logs
* Decision logs
* Incident logs

📌 **Result:**
Mostly `DENY`, sometimes `REQUIRE_FLOW`.

---

## ④ Environment & Change-Control Layer (Operational Safety)

This layer prevents **stupid-but-legal** actions.

### Time-Based Constraints

* Peak hours
* Business hours
* Night ops restrictions
* Weekend restrictions

### Incident Context

* Incident ongoing
* Major incident (SEV-1)
* Degraded state
* Recovery mode

### Environment Awareness

* Production vs staging vs dev
* Canary vs full rollout
* Blue/green switch safety

### Dependency Awareness

* Downstream services affected
* Shared infra impact
* SLA breach risk

### Rate & Frequency Limits

* Restart frequency
* Deploy frequency
* Scaling rate

📌 **Result:**
Mostly `DENY` or `DEFER`.

---

## ⑤ Execution Guardrails (Last-Line Protection)

These protect **after approval**.

### Execution Limits

* Max rows per delete
* Max files per cleanup
* Max pods per restart

### Dry-Run Enforcement

* Preview changes
* Diff required before execute

### Rollback Guarantees

* Rollback plan required
* Snapshot existence check

📌 **Result:**
Limits damage, not policy.
