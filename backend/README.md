# AOSS – Full Compliance & Safety System

### Graph-Based Enforcement for SRE Automation

## 1. What This System Is

AOSS (Automated Orchestration for SRE and System Administration) is a platform where automation actions are governed by **hard constraints**, not by LLM reasoning.

Every action generated by an agent is evaluated against **multiple compliance and safety layers** stored in a **Neo4j graph database**.  
If the graph disallows an action, it **cannot execute**, regardless of intent or approval.

---

## 2. Why Graph-Based Compliance

Traditional policy approaches (YAML, OPA, prompt-based checks) suffer from:

- Easy bypass through reasoning  
- No organizational memory  
- Weak dependency modeling  
- Poor auditability  

Graph-based compliance enables:

- Relationship-aware enforcement  
- Deterministic decisions  
- Long-lived institutional memory  
- Audit and legal defensibility

## 5. Compliance Architecture

Execution follows a strict layered order:

```text
Platform / SRE Safety
        ↓
Organizational Policy
        ↓
Regulatory Compliance (GDPR)
        ↓
Environment & Change Control
        ↓
ALLOW | DENY | REQUIRE_APPROVAL
```

Higher layers override all lower layers.

---

## 6. Layer ① – Platform / SRE Safety (Absolute Guardrails)

These rules are **non-negotiable** and apply to all organizations.

### Always DENY (No Approval Path)

**Destructive System Actions**

* Remove OS
* Format disk
* Wipe cluster
* rm -rf /
* Delete root filesystem

**Security-Critical Actions**

* Disable firewall
* Disable audit logging
* Disable IAM / auth service
* Remove encryption at rest

**Stability Killers**

* Kill all processes
* Stop kube-apiserver
* Stop etcd
* Force reboot all nodes

Result: `DENY`

---

## 7. Layer ② – Organizational Policy (Company Rules)

This layer enforces **who can do what**, based on company governance.

### Inputs

**Roles**

* intern
* automation
* sre
* admin

**Role Permissions**

* Allowed actions per role
* Forbidden actions per role

**Approval Rules**

* Bulk delete
* Schema changes
* Firewall updates
* Network reconfiguration

**Blast Radius Limits**

* SINGLE_RESOURCE
* MULTI_RESOURCE
* GLOBAL

Result: `ALLOW`, `DENY`, or `REQUIRE_APPROVAL`

---

## 8. Layer ③ – Regulatory Compliance (GDPR via Infra Facts)

The system never asks legal questions.
It enforces GDPR by mapping **infrastructure facts**.

---

### 8.1 Services Under Automation

Inputs:

* Service name
* Service type (API, Database, Auth, Logging)
* Environment (prod / staging)
* Owner team

Used for:

* Action scoping
* Targeted blocking
* Audit clarity

---

### 8.2 Data Touch Points (SRE Language)

Instead of “personal data”, the system asks:

**Does this service touch user-identifiable data?**

If yes:

* Email
* IP address
* User ID
* Logs with identifiers

---

### 8.3 Logs, Metrics & Traces

Inputs:

* Log types (access, auth, app)
* Whether logs contain identifiers
* Retention days
* Storage system

Enforced:

* Retention limits
* Prevention of illegal deletion
* Safe observability pipelines

---

### 8.4 Databases & Storage

Inputs:

* Database type (Postgres, MySQL, NoSQL)
* Tables containing user data
* Backup enabled
* Backup retention

Enforced:

* Safe database operations
* Backup coverage
* Erasure propagation

---

### 8.5 Backups, Replicas & Disaster Recovery

Inputs:

* Read replicas
* Geo replicas
* Backup locations
* DR region

Enforced:

* No partial deletion
* No cross-region data leakage

---

### 8.6 Erasure Handling (SRE View)

Instead of “GDPR erasure”, the system asks:

**How fast must all systems comply when user data must be deleted?**

Inputs:

* Erasure SLA (days)
* Systems involved (DB, cache, logs, backups)

This rule is **global**.
If violated → all automation is blocked.

---

## 9. Layer ④ – Environment & Change Control

Prevents **stupid-but-legal** actions.

**Time-Based Constraints**

* Peak hours
* Maintenance windows
* Business hours

**Incident Context**

* Active incident
* SEV-1 freeze
* Recovery mode

**Environment Awareness**

* Production vs staging
* Canary vs full rollout

Result: `DENY` or `DEFER`

---

## 10. How Enforcement Works (End-to-End)

### Example Intent

```json
{
  "action": "DELETE_LOGS",
  "service": "auth-service",
  "role": "sre",
  "scope": "MULTI_RESOURCE",
  "params": { "older_than_days": 120 },
  "data_type": "log",
  "region": "EU"
}
```

### Evaluation Flow

1. Platform / SRE safety checks
2. Organizational policy checks
3. Regulatory compliance checks
4. Environment and change-control checks

Final decision is returned to the executor.

Compliance is not a rule engine.

If the graph disallows an action, **nothing can override it**.
